1. Executive Summary & Testing Philosophy

In mission-critical infrastructure construction management, inaccurate schedule or financial projections can trigger multi-crore contractual claims, unjustified vendor penalties, or flawed resource allocation. Testing this AI decision-support platform required an unwavering architectural principle:

Core Testing Doctrine
Deterministic arithmetic must be mathematically provable; non-deterministic AI must be evidence-grounded and anti-hallucinatory. Mathematical calculations (CPM float, overdue days, cost variance, stock deficits, productivity rates) are tested against hand-calculated ground truths. AI and RAG components are tested to ensure they cite exact verbatim contract clauses and strictly output "Insufficient data" when queries fall outside verified records.

The automated test suite is housed in tests/test_intelligence_agent.py and can be triggered via the single-click PowerShell script .\run_tests.ps1 or directly via python -m pytest.

2. Test Hierarchy & Pyramidal Strategy

The testing suite is structured into four distinct layers ensuring robust coverage from low-level functions to end-to-end integration:

Testing Tier Target Module Primary Objective Test Isolation Method
Layer 1: Unit Tests ScheduleEngine, CostEngine, ProcurementEngine, ContractorEngine Verify arithmetic correctness for dates, float, burn rate, productivity deficit, and budget variance. Isolated synthetic DataFrames with known mathematical ground truths.
Layer 2: Contract & RAG Tests ContractRAGEngine Verify TF-IDF vector indexing, relevance scoring thresholding, and anti-hallucination guards. Structured clause datasets & verified negative (unsupported) queries.
Layer 3: Multi-Agent Logic ProjectRiskSupervisor Verify detection and resolution of inter-agent telemetry contradictions. Synthetic conflicting agent payloads (e.g. on-time with cost overrun).
Layer 4: System Integration ProjectDataLoader, DataQualityChecker, Streamlit App Verify end-to-end ingestion across all 14 attached files and clean dashboard compilation. Full production dataset (12,633 activities, 30 contracts, 15,571 dependencies).

3. In-Depth Breakdown of All 15 Acceptance Test Cases

Test 1: test_date_parsing_and_missing_dates Unit Test PASSED

Business Need: Construction schedules routinely contain incomplete activities where actual_finish is empty. A naive parser might crash, default missing dates to epoch zero, or incorrectly assume the activity took zero days.

Implementation: Injects an activity with actual_finish: "". Tests that pd.to_datetime() does not mutate or crash, preserves pd.isna(actual_finish), correctly classifies is_in_progress == True, and measures overdue days against the cutoff_date.

Test 2 & 3: test_completed_activity_delay Unit Test PASSED

Business Need: A completed activity must have its delay calculated strictly by comparing its actual completion date to its planned completion date, ignoring current reporting cutoff dates.

Implementation: Injects an activity with planned finish 2026-01-10 and actual finish 2026-01-18. Asserts that finish_delay_days == 8, delay_days == 8, and is_overdue == False (because completed tasks are no longer actively overdue).

Test 4: test_incomplete_overdue_activity Unit Test PASSED

Business Need: For ongoing activities, project managers need to know how many days have elapsed past the baseline deadline as of the reporting cycle cutoff date.

Implementation: Injects an in-progress milestone activity with planned finish 2026-03-01 evaluated against a cutoff date of 2026-03-15. Asserts that is_overdue == True, overdue_days == 14, and milestone_delayed == True.

Test 5: test_zero_and_negative_delay Unit Test PASSED

Business Need: The system must handle activities that finish ahead of schedule (negative delay) or exactly on target without producing false-positive delay alerts.

Implementation: Tests two activities: one finishing 4 days early (finish_delay_days == -4) and one finishing on the exact planned date (finish_delay_days == 0). Asserts that both are categorized as ON_TIME with zero penalty points.

Test 6: test_cost_variance_calculation Unit Test PASSED

Business Need: Project leadership requires accurate cost variance and daily burn rate tracking to calculate financial exposure on extended activities.

Implementation: Injects an activity with baseline_cost = 50,000, actual_cost = 65,000, and delay_days = 5. Asserts that cost_variance == 15,000 (30% overrun) and calculates ongoing daily burn rate exposure.

Test 7: test_missing_budget_information Edge Case PASSED

Business Need: Unplanned site activities or emergency work orders may have a baseline budget of zero or null. Dividing by zero would crash the dashboard.

Implementation: Tests an activity with baseline_cost = 0.0 and actual_cost = 10,000.0. Asserts that cost_variance_pct returns 0.0% gracefully without raising a ZeroDivisionError.

Test 8: test_unmatched_procurement_records Edge Case PASSED

Business Need: Not all construction tasks require physical materials (e.g. surveying, site clearance, approvals). Unmatched activities must not trigger false inventory alerts.

Implementation: Queries procurement status for an activity with no matching BOQ rows. Asserts that has_material_requirement == False, materials == [], and has_shortage == False.

Test 9: test_supplier_performance_calculation Unit Test PASSED

Business Need: Procurement teams must distinguish vendor delivery shortages from quality inspection rejections.

Implementation: Supplies 1,000 received units, 900 accepted, and 100 rejected (10% defect rate) with warehouse reserved stock exceeding closing stock by 300 units. Asserts acceptance rate is exactly 90.0% and stock deficit is 300.0 units.

Test 10: test_rag_evidence_retrieval RAG Test PASSED

Business Need: Legal claims must be grounded in exact contractual language with verifiable section and clause identifiers.

Implementation: Indexes Clause 8.4 ("Delay and Liquidated Damages"). Queries with "liquidated damages penalty delay". Asserts top retrieved chunk is Clause 8.4, penalty_applicable == True, and cosine similarity exceeds relevance threshold.

Test 11: test_unsupported_contract_questions Anti-Hallucination PASSED

Business Need: LLM/RAG systems must never invent terms or penalties for out-of-scope inquiries.

Implementation: Queries the contract engine with an out-of-domain prompt: "What is the software license agreement for the Salesforce CRM platform?". Asserts the system returns evidence_retrieved == False and outputs "Insufficient data".

Test 12: test_supervisor_conflict_resolution Agent Test PASSED

Business Need: Specialist agents may report contradictory telemetry that must be detected and reconciled before executive reporting.

Implementation: Feeds the Supervisor an activity with delay_days = 0 but a cost_variance = 50,000. Asserts the Supervisor flags a Cost vs Schedule Discrepancy and explains that the overrun is driven by unit rates rather than schedule delay.

Test 13: test_local_fallback_without_api_credentials Offline Test PASSED

Business Need: The core analytics and RAG capabilities must remain 100% operational offline without external API keys or cloud dependencies.

Implementation: Clears environment API keys, initializes the local TF-IDF retriever, and validates that question answering and clause retrieval function locally without network calls.

Test 14: test_empty_datasets_handling Resilience Test PASSED

Business Need: Corrupted or empty input files must fail gracefully rather than crashing the runtime server.

Implementation: Feeds empty DataFrames into DataQualityChecker and ScheduleEngine. Asserts that the audit score reflects missing data penalties and returns empty structured results safely.

Test 15: test_integration_on_actual_workspace_data Integration Test PASSED

Business Need: Verify that the entire pipeline scales smoothly across the actual 100-project workspace dataset.

Implementation: Ingests the full 12,633-row activities dataset and 15,571 dependencies, executes ScheduleEngine.analyze(), and verifies KPI generation for project PRJ-0001.

Test 16: test_dashboard_module_imports Smoke Test PASSED

Business Need: Ensure that the Streamlit UI script has zero syntax errors, missing imports, or broken symbol links.

Implementation: Compiles dashboard/app.py into Python bytecode using compile() to verify syntactical integrity prior to web server launch.

5. Data Ethics & Test Data Isolation

In compliance with strict data engineering standards, test isolation was maintained through clear boundaries:

  • No Mock Pollution: Synthetic test data is isolated strictly inside individual unit test functions. It is never persisted into the data/raw/ directory or merged with the actual 100-project dataset.
  • Zero In-Place File Mutation: Ingestion and analytics tests operate on read-only in-memory copies of the raw CSVs, preserving original audit trails.
  • Zero Fabrication Rule: Incomplete records return explicit "Insufficient data" status rather than fabricating optimistic metrics to make dashboards look artificially complete.
